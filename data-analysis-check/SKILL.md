# Data Analysis Check — データ分析の検証スキル

データの集計・変換・統計処理を行ったり、他人（他のAI含む）の分析結果をレビューしたりするときに使う検証プロトコル。目的は、人間が目視では気づけない誤り（取り違え・分母の誤り・欠損の黙殺・版の混在）を、機械的な照合で捕まえること。根拠：2026-11-18にユーザーが「チェック項目を整理してスキルとしてまとめておく」ことを承認し作成。設計の元は同日の解説ページ「AIの使い方 — 二つの実践メモから」のデータ分析編（実務編）。2026-11-20に3系統の並行調査（自前調査、Claude、ChatGPT Deep Research）で実務者文献と突き合わせて強化した。

## いつ使うか

- 表データの集計、結合、単位変換、指標計算（密度、CPUE/SPUE、割合など）を行うとき
- モデル入力データの前処理や、推定結果の集計・作表を行うとき
- 自分または他のAIが出した分析結果をユーザーに報告する前に、検証として通すとき

## 手順1：集計前に定義を固定する（手順書ゲート）

コードより前に固定するのは**集計仕様**（定義）である。各ステップの照合件数が入った**手作業手順書**は、件数が実行しないと分からないため、スクリプト実行後に台帳から作る（手順5）。この2つを混同しない。

順序は固定する：

1. **集計仕様のドラフトを提示する。** データ辞書を確認する：各列の意味、単位、欠損の表現、データの出所と版（いつの改訂版か）。集計仕様は日本語・表形式で：何を数えるか（分子）、何で割るか（分母）、除外条件、単位、期間の区切り（年度／暦年）、結合キーと粒度、重複判定キー、日時の書式・タイムゾーン、行列・クロス集計での未観測セルの扱い（0ではなくNA）、実装言語（Python / R）。定義が資料から読み取れない項目は推測で決めず、「仮定」として冒頭に列挙する。ユーザーの確認が要る仮定は確認してから進む。

確認できない仮定が残る場合は、確認の代わりにしないことを前提に、主要な代替案（最大2案）で結果を並べ、見出しの結論（報告の冒頭に出す主要な数値・主張）が反転するかを示す。条件は3つ：何をもって「反転」とするか（増減の向き、順位、管理目標を超えるかどうか等）は結果を見る前に固定する／数字を見てから都合のよい案を選ばない（採用は人間が中身の理由で決め、`source: user` として判断記録に残す）／「反転しない」は、比べた案の範囲内で頑健という意味に限る。反転する仮定は「重要な未確定事項」として報告の冒頭に出し、確定値扱いにしない（手順5の感度表）。
2. **生成とは別のAIに仕様レビューをさせる。** 仕様自体の誤り（分母の定義ミス、結合による行増殖、曖昧な条件）は、後のコード照合では構造的に検出できないため、ここで潰す。指摘を反映してドラフトを直す。
3. **人間が承認する（ゲート）。** 承認の判定は「読んで納得したか」ではなく「定義と抽出条件を自分の言葉で即答できるか」：何を除外したか（WHERE）、指標の分子・分母、結合キーと粒度（結合で行が増えるか）。即答できない定義があれば、コードを書く前に仕様側を直す。根拠：Microsoft ResearchのCHI 2024研究では、AIの説明とコードを照合する行為自体が誤った確信を強める場合があると報告されており、「読んだ」は検証にならない。日本の実務者（Zenn・omochi）も実行前ゲート3点（除外／分子分母／結合粒度）をスキルに固定している。

あわせて分析の**重要度区分**をここで決める（分からなければユーザーに聞く。聞けないときは上の区分として扱う）：

| 区分 | 例 | 必須の検証 |
|---|---|---|
| 通常 | 内部の探索・下見 | 検証表 項目1〜9 |
| 重要 | 報告書・論文の数値、意思決定に使う値 | ＋項目10（独立再計算）、項目11（別AI照合・真値テスト） |
| 間違いが許されない | 公表値、行政提出物 | ＋ゼロベース再実装（手順4）、系の外の錨 |

## 手順2：コード生成時の指定（一回きりの分析）

- 使い捨てが前提。単一ファイル、上から下に読める直線形。再利用前提のモジュール化・抽象化はしない。外部の設定ファイルは作らない（パラメータはファイル冒頭の定数ブロック1か所に置く）。生データ固有のクレンジングは再利用できないので、構造への投資は無駄になる。検証可能性はコードの構造ではなく、各段の中間表と検証表の出力で担保する。
- 関数化は最小限：同じ操作がそのまま繰り返されるときだけ関数にする。繰り返しは素直に for 文で書く。for 文の対象は、ファイル・種・地点・年度など**処理単位の繰り返し**であり、列全体への演算（ベクトル演算）は1行1操作のまま書いてよい。行単位のループが要るかどうかは処理の意味で判断する（2026-11-24にユーザーが明示、2026-11-27に追記）。
- ベタ書き：pandas や tidyverse の公式 example のように1行1操作。中間生成物（データフレーム等）には意味のある名前を付けて各ステップで残し、その場で目で確認できる形にする。ネストした一行処理や、中間状態を隠すチェーン・合成式・関数の内部に埋めない。
- コメント必須：文法の説明ではなく、その処理の目的と判断を書く。読み手は人間（ユーザー本人）であることを前提にする。
- 根拠：プロのデータサイエンティスト14名の観察研究（Henley）では、複数参加者がAIの関数化・パラメータ化をあえて解除して書き戻していた。エージェント生成コードは人間のOSS比で2.2倍冗長という測定もある（SlopCodeBench）。
- 各処理段（結合・除外・集計）の後に、行数と主要列の合計をその場で出力させる。後段の検証表は、各段でスクリプトが出力した値を**スクリプト自身が集めて**作る（人が数字を打ち直さない）。検証表を作るためだけに処理を再実行しない。ただし項目10（独立再計算）は別の経路で計算し直すこと自体が目的なので、この制限の対象外。
- 中間表や集計結果をCSVで出す場合は **BOM付きUTF-8**（Python：`encoding="utf-8-sig"`、R：`readr::write_excel_csv()` または `write.csv(..., fileEncoding="UTF-8-BOM")`）で書き出し、入力もBOM許容で読み込む。

## 手順3：集計後に検証表を出す

結果と必ずセットで、以下の検証を数値の表で示す。「確認しました」とは書かない。

1. **件数チェック**：入力行数、除外・隔離した件数と理由別の内訳、出力行数。レコード単位の工程では 入力 − 除外 − 隔離 = 出力 が一致すること。集約やイベント化で粒度が変わる工程では、「Σ（各出力行が持つ元レコード数）= 入力レコード数」で照合する。
2. **合計照合**：合計が既知の値（公表値、元データの単純合計、過去の確定値）と一致するか。一致しない場合は差分を説明する。
3. **範囲チェック**：主要な列の min / max を示し、ありえない値（負の個体数・密度、1を超える確率、未来の日付）がないか。
4. **単位チェック**：面積（ha / km² / m²）、割合（0–1 / %）、期間（年度 / 暦年）の取り違えがないか。変換した箇所は変換式を書く。
5. **分母チェック**：割合・密度・率の分母が定義どおりか。延べ数と実数の混同、二重計数、対象範囲外の混入がないか。
6. **欠損チェック**：欠損の件数と扱い（除外／0として集計／補完）を明示する。欠損を黙って0にしていないか。行列・クロス集計では、未観測（その期間に調査していない）セルは NA、観測して不在のセルが 0。この2つを区別した件数を示す。
7. **版チェック**：異なる版・改訂の数値を混ぜて接続していないか。特に時系列は同一版で統一されているか。
8. **中間表**：グループ別件数やクロス集計を出し、ドメイン知識から見て異常な偏り（特定の年・地域だけ突出、ゼロの塊）がないか。
9. **トレーサビリティ**：任意の集計値について、元のレコードまで辿れる形（キー、フィルタ条件）を示せること。
   - 複数値を対応表へ展開した場合は、元表の行数と、展開対象の元行数・対応行数を別々に照合する。元表キー、対応表のキーの組、参照先の存在、未対応・複数候補の件数を確認する。結合によって複製された観測値をそのまま合計していないか確かめる。
   - 版や時期により識別子の意味が変わる場合は、名前空間と有効期間を含めて対応表の適用範囲を照合する。元表記、正規化したコード、未確認の空欄を元資料と突き合わせる。
10. **独立再計算**（重要な結果のみ）：別の方法（別の集計経路、手計算できるサンプル数件＝最低3件、うち1件は除外境界の近くのレコード）で同じ値を再現する。
11. **別AI照合と真値テスト**（重要な分析のみ）：
    - 別AIによる手順書⇔コード照合は「不整合の検出」であって「正しさの保証」ではない。異なるモデル同士でも誤りは相関する（両モデルが誤った場合、その60%が同じ誤答だったという実測）。照合AIには生成側の文脈（実装時のプロンプトや言い訳）を共有せず、手順書から独立に期待値（行数・合計・回復すべき値）を導出させてからコードと突き合わせる。
    - 推定・モデリングでは、真値が既知の模擬データを通してパラメータが回復できるか試す。模擬データは生成側と文脈を共有しない別セッションで作る。実例：DiD再実装の変換ミスは真値1.0に対し2.03を返し、通常のチェックをすべて通過したが、真値を植えたシミュレーションだけが暴いた。
    - 「動いた」「エラーが出なかった」は証拠として数えない。OWOXの実験では24回中5件がエラーなしに誤答（空・NULL・0）で、原因はステータス値の大文字小文字と、データに存在しない値の捏造だった。フィルタ条件に書かれたリテラル値は、実データに実在するか必ず確認する。

いずれかの項目が不一致または説明不能なときは、結果表を「確定値」として出さない。検証表の該当行に `NG` と原因の仮説を書き、ユーザーの判断を待つ。

NGを解消するためのコード変更は、原因の仮説と一緒に判断記録（`data-analysis-pipeline` の `decision_log.md`）に残す。除外・結合・定義を変えて数値を一致させる変更は仕様変更であり、ユーザーの承認を経てから行う（検証表をOKにするために処理をいじる「合わせにいく修正」を防ぐ）。

## 手順4：ゼロベース再実装チェック（間違いが許されない分析のみ）

手順が固まった後、元のコードを見せずに、**集計仕様と生データだけ**から別の主体にゼロから再実装させ、清書版を成果物とする。実装ミス（列の取り違え、条件の書き間違い、結合の行増殖）と仕様の曖昧さを捕まえるための最強の照合で、臨床試験の二重入力と同じ理屈。成立条件：

- 再実装側に元のコードを見せない（見ながらの再実行は照合ではなく「なぞり」で、誤った確信を強める）
- **手作業手順書の照合件数、元コードの出力、検証表も、照合が終わるまで渡さない。** 件数を見せると再実装者がそれに合わせて実装を調整してしまい、独立性がなくなる。照合で一致したら、清書版から手作業手順書と検証表を作り直して成果物にする
- 実装者か言語を変える（人間／別モデル／Python⇔R）
- 各工程の照合件数と最終テーブルの全セルdiffで比べ、不一致は原因まで掘る。原因が仕様の曖昧さなら仕様を直す
- 限界も明記する：一致は「仕様どおりに作れた」証明であって「仕様が正しい」証明ではない。Knight & Leveson（IEEE Trans. Software Engineering, 1986）の実験では独立実装でも失敗が相関し、2026-11-20の自前調査でも、両モデルがともに誤った場合に同じ誤答になる割合は約60%だった（項目11と同じ指標）。したがって既知の合計・手計算サンプル・真値テストという「系の外の錨」は別途必ず置く
- 全件再実装はコストが高いので、公表値・行政提出物など stakes の高い分析に限定する。通常の分析は項目10の独立再計算で足りる

## 手順5：出力の形

ユーザーへの報告はこの順序にする。コードは最後に置く。成果物をファイルとして保存する場合は、手作業手順書を `procedure.md`、仕様・検証表・感度表・結果表を `verification.md` とする。

1. 集計仕様（日本語・表形式）と、置いた仮定の列挙
2. 手作業手順書（人間がExcel等の手作業で同じ手順を再現できる作業手順）：実行後に台帳から作り、各ステップに「この時点で○行になるはず」という照合用の件数を付け、必ず同封する。変換手順は、規模的に現実的かどうかは別として、手作業の操作（並べ替え・フィルタ・対応表の引き当て・ピボット・計算列（同じ行内の四則演算と直前行の参照）・行の削除と別シートへの退避）で表現できるものだけにする。文字の正規化（NFKC等）は手順書では「生の表記→正規化後のラベル」を全部列挙した対応表の引き当てとして書き、混在した日時書式は「書式ごとにフィルタ→計算列で変換」として書く（2026-11-24にユーザーが明示）
3. 検証表（手順3の結果、数値で）
4. 中間表（項目8で出したもののうち、異常の判断に使ったもの）
5. 結果表と解釈。結果表には照合列を持たせる：合計行には「照合値（出所）・差・OK/NG」を並べる（例：グループ別合計の総和の隣にファイル全体の合計、密度の隣に分子と分母の実数）。結果表だけが切り取られて使われても、裏付けが一緒に残るようにするためで、照合列は合計行と見出しの数値に限る（全行に付けると表が読めなくなる）。見出しになる数値は、本文中でも検証表の該当項目番号を併記する（例：「捕獲数 1,234頭［検証2：OK］」）。照合列もスクリプトが出力する（人が打ち直さない＝手順2）
6. 感度表（手順1で確認できなかった仮定がある場合のみ：仮定ごとの両案の結果と、見出しの結論が反転するかどうか）
7. コード・コマンド（付録）

変数名には業務用語（日本語）との対応表を付ける。ドメイン専門家がコードを読まずに仕様と検証表だけで判断できることが目標。

## ドメイン固有の落とし穴（野生動物の個体数推定・管理）

- 環境省等の個体数推定値は公表のたびに過去分も遡って再推定される。異なる公表版の数値を接続して時系列にしない（版チェックの最重要例）。
- 密度推定の分母：カメラ設置台数・努力量（カメラ日数）、調査面積の定義。努力量あたり指標（CPUE/SPUE）は分母の定義を必ず書く。
- 年度と暦年：捕獲統計・行政データは年度区切りが多い。暦年の気象データ等と結合するときにずれる。
- 面積単位：ha と km² の取り違えは密度で100倍の誤差になる。
- 行政界の変更・合併があった地域の時系列接続。
- カメラの時計のずれ・電池交換時のリセット：設置期間外の記録や日時の逆行がないか。
- 市区町村コード・メッシュコード・個体IDの先頭0落ち（数値として読むと落ちる。文字列で読む）。
- 未観測のセルを0で埋めると偽の不在になり、占有率・検出率が偏る（項目6）。

## スキル自体の保守

- このスキルが本当に誤りを捕まえるかは、既知の答えがあるデータ（合計や結果が公表されているもの）で手順を通して確かめる。わざと誤り（単位の取り違え、版の混在）を含むテストデータで試すのも有効。
- 実際に誤りが起きたり、ユーザーが新しい落とし穴を指摘したりしたら、そのパターンをチェック項目か「落とし穴」に追加する。項目を消すときは理由を添える。
